## 2. 目标产品定义

AlPage 当前应被定义为：

**一个面向售前人员的 Portal Agent 工作台。**

Theme Studio 是历史名称。后续用户可见主产品 UI、后台 admin 页面、产品文档和实现计划均逐步统一为 AlPage。

AlPage 的目标不是让用户先理解项目、模板、导出规则，也不是让用户围绕主题包打包来完成工作，而是：

- 售前人员进入产品后，通过对话描述当前客户需求
- 对话过程中可上传图片、Word、PDF 等资料辅助理解
- Agent 通过追问、选项和补充表单收集客户信息
- 只有在客户关键信息足够后，Agent 才生成门户方案
- 生成前先给出摘要确认
- 生成结果是一份可持续编辑的 `PortalPlan`，包含：
  - 企业资料和行业上下文
  - 主题层
  - 工作区规则层
  - 卡片内容层
  - 编辑历史与最终门户状态
- 用户围绕这份 `PortalPlan` 继续修改
- 修改方式同时包含：
  - 对话式编辑
  - 配置式编辑（三个 tab：主题、工作区规则、卡片内容）
- 用户满意后全屏查看结果
- 后续进入保存、分享、再次编辑
- 保存门户时，系统自动静默沉淀行业案例到服务端 SQLite
- 后续类似行业生成时，Agent 可按行业 + 关键词检索历史案例作为参考

一句话描述：

> **售前围绕单个客户收集信息，由 Portal Agent 生成可继续使用、持续演进并可沉淀复用的 PortalPlan。**

## 3. 后续统一口径

后续无论是人还是大模型，在描述产品时都应优先使用下面这条主链路：

```text
售前进入 AlPage
→ 通过对话输入客户需求（可上传资料）
→ Agent 收集并补齐客户信息
→ 输出摘要确认
→ 生成 PortalPlan
→ 展示门户预览
→ 用户继续迭代（对话式编辑 / 配置式编辑）
→ 全屏查看
→ 保存 / 分享 / 再次进入编辑
→ 保存时自动静默沉淀行业案例
```

生成前必须补齐的客户信息包括：

- 客户名称
- 客户行业
- 客户核心职能/业务特征
- 本次门户用途
- 希望突出哪些卡片或信息
- 品牌/视觉倾向

禁止再把下面这些说法当作产品主链路：

- 先创建项目再开始
- 先选产品版本再继续
- 用户完成目标的核心是打包导出
- 产品本质是主题包生成服务
- 生成结果只是一套主题或一张预览图

可以保留但必须降级的说法：

- 项目持久化
- 工作区状态保存
- 底层截图链路
- 打包与导出能力
- Theme Studio 历史名称

这些能力是**现有实现或历史叙事的一部分**，但不应继续作为产品叙事中心。

## 4. 当前代码现状

基于当前仓库代码，产品现状更接近“主题设计/导出工具向 AlPage Portal Agent 工作台过渡中”的状态。

### 4.1 已有能力

- 有“直接开始创作”的落地页语义，用户进入后会看到“开始新创作”
- 有项目与工作区持久化能力
- 有工作区卡片编辑能力
- 有卡片库、拖拽、缩放、删除、属性编辑
- 有 AI 对话修改链路
- 有预览能力
- 有上传资料和聊天上下文能力基础，可作为后续客户信息收集入口
- 有 Express + SQLite 服务端基础，可承接行业案例库 MVP

### 4.2 仍然很强的旧主线

- 代码里仍然保留明显的项目模型
- 代码里仍然保留完整的打包弹窗与导出流程
- 预览语义仍然以 OA 主题页面为核心，不是“完整新门户结果”
- 现有结果使用链路更偏“保存项目/导出产物”，不是“保存 PortalPlan / 分享门户 / 沉淀案例”
- 运行中 Agent 仍可能保留“主题设计师 / Theme Agent”口径
- 用户可见 UI 和后台 admin 页面仍可能存在 Theme Studio 或主题自动化命名

### 4.3 明显缺失的目标能力

- `PortalPlan` 作为统一状态模型尚未落地
- 全屏查看门户的正式产品链路
- 分享能力
- 围绕“PortalPlan”的明确保存心智
- 从需求直接生成“完整门户结构”的强产品表达
- 生成前对客户信息完成度的明确门槛
- 摘要确认机制
- 根据客户行业、企业属性和门户用途动态生成卡片结构与示例内容
- 三层配置面板：主题、工作区规则、卡片内容
- SQLite 行业案例库的保存与检索接口

## 5. 差距清单

### 差距 1：产品起点虽已接近，但底层心智仍是“项目”

目标：

- 用户进入 AlPage 后直接开始描述需求，不需要先理解项目概念

现状：

- 体验层已经有“开始新创作”
- 但底层状态仍然明显以 `project` 为核心，当前工作区、主题、导出任务都挂在项目模型上

判断：

- **部分达成**

结论：

- 可以保留项目作为技术持久化单位
- 但产品表达应继续弱化“项目先行”

### 差距 2：目标是“生成 PortalPlan”，现状更像“生成主题预览 + 固定工作区”

目标：

- 系统在信息足够后直接生成一份可持续编辑的 `PortalPlan`

现状：

- 当前生成链路仍然强依赖背景图、配色、登录页 / 工作台模板
- 默认工作区卡片是预设好的固定模板组合，不是按需求动态生成完整门户结构
- 示例内容仍缺少明确的行业/企业适配逻辑

判断：

- **核心未达成**

结论：

- 这是当前产品与目标之间最大的差距

### 差距 3：Agent 仍偏 Theme Agent，不是面向售前的 Portal Agent

目标：

- Agent 先补齐当前客户信息，再生成门户方案
- Agent 的目标是 `PortalPlan`，不只是主题

现状：

- 文档和代码中仍可能保留 Theme Agent / 主题设计师表述
- 当前能力仍以图像和配色生成作为主任务
- 缺少“客户信息足够才生成”的硬门槛与摘要确认

判断：

- **核心未达成**

结论：

- 如果不先修正 Agent 目标，后续实现仍会滑回“主题生成器”方向

### 差距 4：直接编辑能力需要升级为三层配置编辑

目标：

- 用户可直接编辑主题、工作区规则和卡片内容，并写回同一份 `PortalPlan`

现状：

- 已经有卡片拖拽、缩放、删除、属性修改、卡片库新增
- 但整体仍更像“工作区编辑器 Phase 1”，不是成熟的三层门户编辑体验

判断：

- **已部分达成，需继续产品化**

结论：

- 应继续往“门户编辑”而不是“内部工作区编辑工具”方向推进

### 差距 5：全屏查看基本缺失

目标：

- 用户满意后，可全屏查看门户，作为结果确认入口

现状：

- 当前代码没有明确的浏览器全屏或产品级全屏查看链路
- 现有的 `expandPreview()` 更像工作台内展开预览，不等于正式全屏结果查看

判断：

- **未达成**

结论：

- 这是需要补齐的明确产品能力

### 差距 6：分享能力缺失

目标：

- 门户结果可分享

现状：

- 代码里没有明确的分享入口、分享动作或分享对象抽象

判断：

- **未达成**

结论：

- 分享是结果使用阶段的重要缺口

### 差距 7：保存与再次编辑具备技术基础，但对象需要升级为 PortalPlan

目标：

- 用户把“生成后的 PortalPlan”视为可保存、可再次进入编辑的成果
- 保存门户时系统自动静默沉淀行业案例

现状：

- 项目和工作区会保存到本地与服务端
- 但产品语言仍更多在说“项目保存”“导出批次”，不是“PortalPlan 保存 / 案例沉淀”

判断：

- **技术上部分具备，产品表达未完成**

结论：

- 需要把保存对象从“项目/任务”重新命名为“门户结果/PortalPlan”

### 差距 8：打包导出仍然占据强入口，和当前目标相冲突

目标：

- 打包导出不再是主产品叙事中心

现状：

- `package-manager.ts`、导出任务、导出桥接、进度弹窗等仍然是显性主链路
- 多个测试和模块都围绕导出闭环展开

判断：

- **与目标明显冲突**

结论：

- 打包能力可以继续保留
- 但在产品定位和后续实现优先级上，应从“主路径”降为“底层能力/附加能力”

### 差距 9：用户可见命名还未统一为 AlPage

目标：

- 主产品 UI、后台 admin 页面、产品文档和后续实现计划统一使用 AlPage

现状：

- 文档和界面中仍有 Theme Studio、主题自动化等历史命名

判断：

- **未完成**

结论：

- 命名切换不是单纯文案改动，它会影响用户对产品主线的理解

---

## 6. 当前最关键的目标差距

如果只看最重要的 6 个差距，优先级如下：

1. **核心产物还不是 PortalPlan**
2. **Agent 仍不是真正的 Portal Agent**
3. **生成前缺少客户信息门槛与摘要确认**
4. **三层编辑模型尚未落地**
5. **全屏查看与分享能力未形成正式链路**
6. **保存门户时的 SQLite 行业案例沉淀尚未落地**

---

## 7. 后续模型必须遵守的表达规则

后续接手模型在回答用户、写文档、做产品讨论时，必须遵守：

1. 先区分“目标产品”与“当前实现”
2. 讨论产品目标时，使用 “AlPage / 面向售前的 Portal Agent 工作台”
3. 讨论当前代码时，明确说明“仍残留主题设计/导出工具心智”
4. 不要再把“主题包生成服务”当成当前对外产品定义
5. 不要把“打包导出”写成用户完成主要任务的标准终点
6. 不要把“Theme Studio”作为未来用户可见主名称
7. 讨论改造方向时，优先围绕：

- 客户信息收集与摘要确认
- `PortalPlan` 生成
- 主题层、工作区规则层、卡片内容层
- 门户级预览
- 对话式编辑与配置式编辑
- 全屏确认
- 保存 / 分享 / 再次编辑
- SQLite 行业案例库静默沉淀与检索

---

## 8. 一句话总结

**目标产品已经切到 AlPage：面向售前的 Portal Agent 工作台；当前实现仍明显带有“主题设计与导出工具”的历史壳。后续所有大模型接手时，都必须先承认这个差距，再围绕 PortalPlan、三层编辑和行业案例库继续推进。**

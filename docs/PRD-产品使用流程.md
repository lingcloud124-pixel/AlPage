# AlPage 产品使用流程

> 版本：v2.0
> 更新日期：2026-05-29
> 适用对象：产品经理、项目负责人、方案设计人员、研发同学

---

## 1. 文档目的

本文档用于统一 AlPage 的产品流程口径，回答四个问题：

- 用户进入产品后先做什么
- 系统如何从需求生成一份 `PortalPlan`
- 用户如何通过对话式编辑和配置式编辑继续修改门户
- 门户生成完成后如何进入保存、分享、再次编辑和行业案例沉淀

本文档面向产品与项目视角，不展开实现细节。

---

## 2. 产品定义

### 2.1 一句话定义

**AlPage 是一个面向售前人员的 Portal Agent 工作台。**

Theme Studio 是历史名称。后续用户可见主产品 UI、后台 admin 页面、产品文档和实现计划均逐步统一为 AlPage。

售前围绕某个客户输入需求，并可在对话中上传图片、Word、PDF 等资料。系统会先补齐客户信息、给出摘要确认，再生成一份 `PortalPlan`；用户可以一边预览，一边通过对话或配置面板持续调整，满意后全屏查看，并进入保存、分享、再次编辑和行业案例沉淀阶段。

### 2.2 产品价值

- 降低售前生成客户门户方案的门槛
- 把复杂配置收在系统内部，让用户直接从客户需求进入创作
- 同时提供对话式编辑和配置式编辑两种调整方式
- 让生成结果可以被保存、分享、持续迭代和行业复用，而不是一次性产物

### 2.3 产品边界

当前版本要做：

- 用户进入产品后直接输入需求
- 系统在对话过程中收集必要信息
- 信息足够后生成一份 `PortalPlan`
- 展示由 `PortalPlan` 派生的门户预览界面
- 支持通过对话继续调整门户
- 支持通过配置面板编辑主题、工作区规则和卡片内容
- 支持全屏查看生成后的门户
- 支持保存、分享和再次进入编辑
- 保存门户时自动静默沉淀行业案例
- 行业案例库第一版按行业 + 关键词检索

当前版本不做：

- 让用户先创建项目后才能开始创作
- 让用户先经历复杂配置再生成结果
- 把产品主链路定义成导出主题包
- 让 `.pen` / Pencil 成为用户流程中的必要步骤
- 复杂全文搜索、默认脱敏、精细权限和高级案例运营后台

## 3. 目标用户

主要用户包括：

- 售前人员
- 方案设计人员
- 实施顾问
- 需要快速产出客户方案的业务同学

这些用户的共同特点：

- 更关注页面结果和生成效率，不关注底层技术细节
- 需要面对多个不同客户快速产出门户初稿
- 希望从客户需求快速进入可看的门户界面
- 需要边看边改，而不是一次提交后被动等待

---

## 4. 核心流程总览

AlPage 的产品模型是：

```text
售前进入 AlPage
→ 对话输入客户需求（可上传资料）
→ 系统收集足够客户信息
→ 摘要确认
→ 生成 PortalPlan
→ 展示门户预览
→ 用户继续迭代（对话式编辑 / 配置式编辑）
→ 全屏查看
→ 保存 / 分享 / 再次进入编辑
→ 保存时自动静默沉淀行业案例
```

这不是“先建项目、再导出、再结束”的流程，而是“客户需求输入 -> 信息补齐 -> 摘要确认 -> PortalPlan 生成 -> 预览迭代 -> 全屏确认 -> 结果使用 -> 案例沉淀”的闭环过程。

## 5. 用户主链路

### 5.1 进入产品

售前进入 AlPage 后，直接进入可创作状态。

用户目标：

- 尽快开始描述当前客户想要的门户

系统负责：

- 展示输入入口
- 提供必要的引导信息
- 保持操作起点足够直接

### 5.2 输入需求

售前通过自然语言描述当前客户想要的门户，也可以补充参考信息。

常见输入示例：

- 给一家制造企业做一个运营门户
- 给一个医疗客户做一个门户方案
- 给一个篮球活动做一个专题门户
- 给一个春节营销客户做一个活动门户

用户目标：

- 用尽量低的表达成本启动生成

系统负责：

- 理解当前客户需求
- 在必要时补充收集客户关键信息
- 为后续生成建立上下文

生成前至少要补齐：

- 客户名称
- 客户行业
- 客户核心职能/业务特征
- 本次门户用途
- 希望突出哪些卡片或信息
- 品牌/视觉倾向

收集方式可以混合使用：

- 对话提问
- 选项选择
- 一次性补充表单
- 上传图片、Word、PDF 等资料辅助理解

### 5.3 摘要确认

当系统认为信息已经足够时，不会立刻生成，而是先给出摘要确认。

摘要至少包含：

- 客户名称
- 客户行业
- 客户核心职能/业务特征
- 本次门户用途
- 重点卡片/重点信息
- 品牌/视觉倾向
- Agent 对门户结构的理解
- Agent 对页面风格的理解

用户目标：

- 在生成前确认系统理解的是不是当前客户的真实诉求

系统负责：

- 整理已收集信息
- 暴露缺失项和假设项
- 在确认后进入 `PortalPlan` 生成

### 5.4 生成 PortalPlan

当系统认为信息已经足够时，直接生成一份 `PortalPlan`，而不是只给用户抽象描述或零散素材。

用户目标：

- 直接看到一个可继续使用、可继续修改的门户方案

系统负责：

- 组织页面结构
- 生成门户内容与视觉方案
- 输出一个可预览的完整门户方案
- 让示例内容跟随客户行业和企业属性变化

输出结果：

- 一份 `PortalPlan`
- 主题层：视觉主题、页眉、导航、banner 等
- 工作区规则层：卡片圆角、间距、密度、栅格、布局模式、区域位置和大小
- 卡片内容层：行业/企业适配的卡片标题、摘要、列表项、链接和映射理由
- 对应的工作区预览界面

### 5.5 预览门户

`PortalPlan` 生成后，系统展示门户预览界面，用户可以先整体判断方向是否正确。

用户目标：

- 快速确认门户是否接近预期

系统负责：

- 让用户看到完整门户效果
- 提供清晰的工作区视图
- 支持后续进入调整动作

### 5.6 持续调整

如果门户还不够满意，用户可以继续修改。

当前支持两种主要方式：

1. **对话式编辑**
   - 让系统改风格
   - 让系统改布局
   - 让系统改内容表达

2. **配置式编辑**
   - 编辑主题层
   - 编辑工作区规则层
   - 调整卡片所在区域、位置和大小
   - 编辑卡片内容层

用户目标：

- 在已有门户基础上快速迭代，而不是每次从头生成

系统负责：

- 保持修改结果即时可见
- 保持对话式编辑与配置式编辑可以衔接
- 让两种编辑方式都写回同一份 `PortalPlan`

### 5.7 配置编辑模式

用户点击“编辑配置”时：

- Agent 对话区自动收起为窄栏或入口按钮
- 中间保留门户预览
- 右侧打开配置面板
- 配置面板包含三个 tab：主题、工作区规则、卡片内容
- 首次进入主题面板，之后记住上次编辑的 tab

用户点击 Agent 入口或“返回对话”时：

- 关闭配置面板
- 展开 Agent 对话
- Agent 继续基于当前 `PortalPlan` 修改门户

对话和配置面板不同时展开，避免界面拥挤。

### 5.8 全屏查看

当用户觉得当前结果已经足够好时，可以全屏查看生成后的门户。

用户目标：

- 以更完整的沉浸式方式确认最终效果

系统负责：

- 提供全屏查看入口
- 保持全屏视图与 `PortalPlan` 派生结果一致

### 5.9 结果使用与案例沉淀

全屏查看不是流程终点，后续还会进入结果使用阶段。

用户可执行的动作包括：

- 保存当前门户
- 分享当前门户
- 再次进入编辑

用户目标：

- 让生成结果成为可持续使用的资产

系统负责：

- 保存当前 `PortalPlan`
- 保存门户时自动静默沉淀行业案例
- 提供分享能力
- 支持后续重新打开并继续编辑

案例沉淀规则：

- 保存门户时自动触发
- 不在 UI 上额外提示用户
- 案例库第一版接入服务端 SQLite
- 检索第一版按行业 + 关键词完成

## 6. 关键状态定义

AlPage 当前至少包含六个关键状态：

- **需求输入态**：售前正在描述客户需求，系统持续补充收集信息
- **摘要确认态**：系统整理对客户和门户的理解，等待确认
- **PortalPlan 生成态**：系统正在把需求转成一份完整 `PortalPlan`
- **门户编辑态**：用户围绕已生成门户继续对话式编辑或配置式编辑
- **结果使用态**：用户对当前结果满意后，进入全屏查看、保存、分享、再次编辑
- **案例沉淀态**：保存门户时，系统静默把当前 `PortalPlan` 快照写入行业案例库

关键约束：

- 核心产物必须是“一个客户化 PortalPlan”，而不是只停留在文字或零散建议
- 用户必须可以在预览结果上继续修改，而不是只能重新生成
- 对话式编辑和配置式编辑必须操作同一份 `PortalPlan`
- 全屏查看应服务于结果确认，不应切断后续保存与再编辑链路
- 生成前必须补齐客户信息并完成摘要确认

## 7. 模块职责划分

### 7.1 AI 负责

- 理解当前客户需求
- 在过程中补足必要客户信息
- 输出摘要确认
- 生成 `PortalPlan`
- 响应后续对话式修改
- 根据行业 + 关键词参考历史案例

### 7.2 产品功能负责

- 提供输入与预览界面
- 提供选项收集与补充表单
- 承载配置式编辑能力
- 提供全屏查看能力
- 承接保存、分享和再次进入编辑
- 保存门户时静默沉淀行业案例

### 7.3 用户负责

- 提供客户需求与反馈
- 判断摘要和生成结果是否符合预期
- 选择通过对话还是配置面板继续调整
- 在满意后决定保存、分享或继续编辑

## 8. 输入与输出

### 8.1 输入

- 用户自然语言需求
- 上传的图片、Word、PDF 等参考资料
- 系统整理的摘要确认信息
- 用户对当前门户的调整指令
- 用户在配置面板中的三层编辑操作

### 8.2 输出

- 一份 `PortalPlan`
- 门户的主题层
- 门户的工作区规则层
- 门户的卡片内容层
- 门户预览界面
- 可持续编辑的工作区状态
- 全屏查看结果
- 可保存、可分享、可再次编辑的门户成果
- SQLite 行业案例库中的案例快照

## 9. 成功标准

一次完整流程闭环至少满足以下条件：

1. 售前进入 AlPage 后可直接输入客户需求
2. 系统可补齐并判断 6 项客户信息是否足够
3. 系统可在生成前给出摘要确认
4. 系统可在信息足够后生成一份 `PortalPlan`
5. 用户可在预览界面继续通过对话式编辑修改门户
6. 用户可通过配置面板编辑主题、工作区规则和卡片内容
7. 用户可全屏查看生成结果
8. 用户可对结果执行保存、分享和再次进入编辑
9. 保存门户时，系统可自动静默沉淀行业案例
10. 后续生成时，系统可按行业 + 关键词检索历史案例作为参考

## 10. 风险与约束

需要持续关注的风险点：

- 用户输入需求后迟迟得不到完整门户
- 客户信息没有补齐就开始生成，导致门户方向跑偏
- 生成结果只能看不能改
- 对话式编辑与配置式编辑互相打架
- 配置面板维护了独立状态，导致和 `PortalPlan` 不一致
- 全屏查看后无法顺畅回到保存或继续编辑
- 保存门户后未能沉淀案例，导致行业案例库无法积累

对应原则：

- 创作起点必须足够直接
- 生成前必须补齐客户信息并做摘要确认
- 生成结果必须是完整 `PortalPlan`
- 调整方式必须双通道并能衔接
- `PortalPlan` 必须是唯一事实源
- 结果确认之后必须进入可使用、可管理、可沉淀的阶段

# 页眉与左导航图片三明治处理计划

## 1. 背景与目标

基于 `/Users/le/Desktop/图片处理规则.docx` 与 `/Users/le/Desktop/Map1.pdf` 的要求，新增一条“图片三明治处理”能力，用 `Python + JSON` 的方式统一生成主题包中的页眉与左侧导航图片。

本能力的目标不是改造整条打包链路，而是在现有 `theme_builder.py` 基础上，补齐“按规则生成页眉/左导航背景图”的中间处理层，确保：

- 输入来源统一：使用 2.生成阶段中“当前项目已确认的背景图”和已确认的变量色值。
- 输出位置统一：按不同产品包的目录和命名规则，生成对应 PNG/JPG 文件。
- Light / Dark 规则分离：同一套处理框架，不同主题类型走不同配方。
- 相同尺寸复用：同尺寸或同裁切策略的目标图尽量共用处理模板，避免散落硬编码。
- 登录页背景图不纳入本次处理范围。

## 2. 本次范围

### 2.1 包含

- 页眉相关切图处理
- 左侧导航相关切图处理
- MK 与 EKP 两类产品的图片输出映射
- 基于 JSON 的规则配置与尺寸映射
- 基于 Python 的图层合成、裁切、缩放、导出

### 2.2 不包含

- 登录页背景图处理
- 图标重着色逻辑改造
- 封面图、缩略图整体方案重做
- Web 端创建/预览流程改造

## 3. 需求归纳

### 3.1 图片三明治规则

#### Light

左侧导航：

1. 第一层：底色 `tlayout-header-bg-extend-color`
2. 第二层：项目当前选定背景图
3. 第三层：纵向渐变遮罩
   - 渐变主色：`tlayout-header-bg-extend-color`
   - 兜底色：`#F1F1F1`
   - 透明度：`100% -> 70%`

页眉：

1. 第一层：底色 `tlayout-header-bg-extend-color`
2. 第二层：项目当前选定背景图
3. 第三层：横向渐变遮罩
   - 渐变主色：`tlayout-header-bg-extend-color`
   - 兜底色：`#F1F1F1`
   - 透明度：`60% -> 100%`

#### Dark

左侧导航：

1. 第一层：底色 `header-font-color`
2. 第二层：项目当前选定背景图
3. 第三层：纵向渐变遮罩
   - 渐变主色：`header-font-color`
   - 兜底色：`#F1F1F1`
   - 透明度：`100% -> 70%`

页眉：

1. 第一层：底色 `portal-header-complex-bg-extend-color`
2. 第二层：项目当前选定背景图
3. 第三层：横向渐变遮罩
   - 渐变主色：`portal-header-complex-bg-extend-color`
   - 兜底色：`#F1F1F1`
   - 透明度：`60% -> 100%`

### 3.2 Map1.pdf 提供的补充信息

Map1 说明了当前打包素材的组织关系，核心结论如下：

- 整套变量色值来自“2.生成阶段用户确认”的结果。
- 登录包背景图来自当前项目背景图裁切，但不在本次处理范围内。
- “各种页眉导航切图”应基于当前项目背景图做图片处理，再按样例包尺寸与目录规则落盘。
- MK 与 EKP 的输出命名不同，但部分尺寸与用途相同，适合抽象为“尺寸配方 + 输出映射”两层。
- EKP V14-V16 的页眉类资源落在 `images/image-style/`。
- MK 主题包还涉及若干 sample thumbnail 产物，后续可复用相同裁切结果，但本次主任务应先聚焦真正进入主题包的页眉/侧栏底图。

## 4. 与现有代码的衔接判断

结合 `/Users/le/Desktop/AI主题化/Topic Automation/theme_builder.py` 的现状，可确定：

- 当前脚本已经有图片替换入口，但页眉/侧导航图更多是“直接替换已有文件”。
- 现有替换点包括：
  - `header-banner.png`
  - `header-classic.png`
  - `header-simple.png`
  - `header-tabs.png`
  - `header-sideheader.png`
  - `images/image-style/*`
- 当前脚本也已经识别 MK 与 EKP 的不同目录结构，适合继续承载最终写入逻辑。
- 当前脚本已具备 Pillow 可选依赖检查，适合在同一脚本中新增图片合成模块，或者提炼成独立 `lib` 模块后由 `theme_builder.py` 调用。

结论：本次应优先采用“新增独立图片处理模块 + 在 `theme_builder.py` 中接入”的方式，而不是把逻辑散写进替换代码块中。

## 5. 设计方案

### 5.1 总体架构

建议拆成三层：

1. 规则层：JSON
2. 算法层：Python 图片处理
3. 接入层：`theme_builder.py`

职责分别是：

- JSON 负责描述主题类型、图层规则、裁切尺寸、输出目标。
- Python 模块负责执行“三明治合成 + 裁切缩放 + 导出”。
- `theme_builder.py` 负责读取当前项目配置，并把生成结果写入具体包目录。

### 5.2 建议新增文件

- `config/image-sandwich-rules.json`
- `config/image-output-mapping.json`
- `scripts/lib/image_sandwich.py` 或 `src/...` 下等价 Python 模块

如希望减少配置文件数量，也可以合并成一个 JSON，但从维护性看，建议规则与输出映射拆开。

## 6. JSON 配置设计

### 6.1 规则配置示意

```json
{
  "light-ui": {
    "sidebar": {
      "baseColorVar": "tlayout-header-bg-extend-color",
      "gradientColorVar": "tlayout-header-bg-extend-color",
      "fallbackColor": "#F1F1F1",
      "gradientDirection": "vertical",
      "gradientOpacityStart": 1.0,
      "gradientOpacityEnd": 0.7
    },
    "header": {
      "baseColorVar": "tlayout-header-bg-extend-color",
      "gradientColorVar": "tlayout-header-bg-extend-color",
      "fallbackColor": "#F1F1F1",
      "gradientDirection": "horizontal",
      "gradientOpacityStart": 0.6,
      "gradientOpacityEnd": 1.0
    }
  },
  "dark-ui": {
    "sidebar": {
      "baseColorVar": "header-font-color",
      "gradientColorVar": "header-font-color",
      "fallbackColor": "#F1F1F1",
      "gradientDirection": "vertical",
      "gradientOpacityStart": 1.0,
      "gradientOpacityEnd": 0.7
    },
    "header": {
      "baseColorVar": "portal-header-complex-bg-extend-color",
      "gradientColorVar": "portal-header-complex-bg-extend-color",
      "fallbackColor": "#F1F1F1",
      "gradientDirection": "horizontal",
      "gradientOpacityStart": 0.6,
      "gradientOpacityEnd": 1.0
    }
  }
}
```

### 6.2 输出映射示意

```json
{
  "mk": {
    "headerSimple": {
      "recipe": "header",
      "size": [1600, 572],
      "targets": ["header-simple.png"]
    },
    "headerSideheader": {
      "recipe": "sidebar",
      "size": [1600, 572],
      "targets": ["header-sideheader.png"]
    }
  },
  "ekp_v14_16": {
    "bannerPersonal": {
      "recipe": "header",
      "size": [1600, 572],
      "targets": ["images/image-style/banner_personal.png"]
    }
  }
}
```

设计原则：

- `recipe` 只区分“header / sidebar”这类处理语义，不直接绑定具体文件名。
- `size` 描述目标尺寸。
- `targets` 允许同一张处理结果输出到多个路径。
- 可增加 `cropMode`、`focus`、`format`、`quality` 字段，避免后续再改结构。

## 7. Python 处理流程

### 7.1 输入

- 当前项目背景图绝对路径
- 当前主题类型：`light-ui` 或 `dark-ui`
- 当前项目变量色值字典
- 当前目标产品类型：MK / EKP 各版本
- 输出目录

### 7.2 核心步骤

1. 读取背景图
2. 按输出配置计算目标尺寸
3. 生成裁切底图
   - 建议默认 `cover` 裁切
   - 中心裁切作为第一版默认策略
   - 后续如需要可支持顶部偏移或焦点坐标
4. 生成第一层纯色底图
5. 叠加第二层背景图
6. 生成第三层渐变遮罩
7. 进行 alpha 合成
8. 导出到所有目标路径

### 7.3 建议封装的函数

```python
load_rules(...)
resolve_color(...)
resize_cover(...)
build_gradient_overlay(...)
compose_sandwich(...)
export_targets(...)
generate_theme_images(...)
```

## 9. 验收标准

- 仅处理页眉与左侧导航，不误伤登录背景图逻辑。
- Light / Dark 的底色来源、渐变方向、透明度符合规则文档。
- 相同 recipe + 相同尺寸的图可复用，不出现多处硬编码重复实现。
- MK 与 EKP 输出文件名和目录正确。
- 输出图尺寸与样例包要求一致。
- 缺少依赖或配置时有明确报错信息。
- 在 `theme_builder.py` 主流程中可自动执行，无需人工补图。

## 10. 风险与注意事项

- 当前文档中提到的 `tlayout-header-bg-extend-color` 命名，需确认与实际变量字典中的 key 是否完全一致；如存在前缀差异，应在解析层做兼容。
- Map1 里除了主题包主图，还提到 sample thumbnail，这部分与“页眉/左导航正式资源”边界要先划清，避免首版范围膨胀。
- 若不同产品虽然尺寸相同，但视觉焦点区域不同，后续可能需要引入 `focus` 或“裁切安全区”配置。
- 若目标文件有 PNG/JPG 混用，应在导出层明确颜色模式与压缩质量，避免透明通道丢失或文件体积异常。

## 11. 建议的近期执行顺序

1. 先梳理 `theme_builder.py` 中所有页眉/左导航目标文件，产出映射表。
2. 再定义 `image-sandwich-rules.json` 与 `image-output-mapping.json`。
3. 完成 Pillow 三层合成原型，并用 1 张背景图生成 2 张样例图。
4. 接入 `theme_builder.py`，先打通 1 个 Light 包和 1 个 Dark 包。
5. 最后做版本扩展和异常处理。

## 12. 结论

这项需求本质上是为现有主题打包链补上一层“规则驱动的背景图加工引擎”。最合适的实现方式不是继续堆文件级替换判断，而是把“处理规则、尺寸配方、输出映射”抽成 JSON，把“图层合成与裁切”收敛到统一的 Python 模块里，再由 `theme_builder.py` 调用。

这样可以同时满足：

- 文档要求的 `py + json`
- Light / Dark 差异化处理
- MK / EKP 的不同命名与目录结构
- 后续扩展更多页眉样式时的低成本维护

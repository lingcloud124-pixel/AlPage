## 1. 本次外部资料整理的结论

这批外部资料最重要的价值，不是“补几条零散规则”，而是明确了四类核心知识：

1. **Dark-UI 颜色规则并不等于全部走全局变量**
2. **Pen 切图节点、输出文件名、尺寸与样例包路径有严格对应关系**
3. **页眉类型存在设计参考名称、样例包命名、CSS 类名三套命名体系**
4. **打包系统应该分层，不应把设计、配置、执行、编排混在一起**

## 2.2 Dark-UI 登录页特殊规则

这是本批资料里最容易被忽略、但最重要的发现之一。

### 关键结论

> **Dark-UI 登录页并不是所有颜色都直接引用全局主题变量。**

历史资料明确指出，登录页存在一组**模块专用硬编码色**，尤其是：

- `#f8c28c`
- `#fdd0a3`

它们被用于：

- 欢迎语
- 输入框底线
- 登录按钮背景
- 登录按钮 hover
- 登录辅助链接

### 这意味着什么

后续实现中不能简单假设：

```text
Dark-UI 登录页 = 全局变量直接映射
```

更准确的规则应该是：

```text
Dark-UI 登录页 = 全局变量 + 登录专用强调色
```

### 实施建议

后续代码中应显式保留一层：

- `darkUiSpecialColors.login.*`

而不是把这些颜色悄悄散落到模板 CSS 中。

## 4. 页眉类型关系整理

来源：`页眉类型对照总表.md` 及各页眉对照表

## 4.1 当前存在三套命名体系

同一个页眉，在系统里通常同时存在：

1. **设计参考稿里的节点或设计名称**
2. **样例包中的输出文件名**
3. **运行时 CSS 类名**

例如：

| 概念层 | 示例 |
|--------|------|
| 设计参考稿 | 默认页眉 / 经典页眉 / 简洁页眉 |
| 样例包 | `header_tlayout_frame_bg.png` / `header_complex_frame_bg.png` |
| CSS 类名 | `.lui_tlayout_header` / `.lui_portal_header_complex_frame` |

### 实施结论

后续必须建立显式关系表，不能靠口头记忆。

## 5. 打包层架构规则整理

来源：`Python打包分层方案_初稿.md`、`manifest字段定义_初稿.md`、`主题包层级关系说明_初稿.md`、`Trae职责说明_初稿.md`

## 5.1 五层分工

历史资料把整个系统拆成五层，这个拆法是合理的：

1. **设计源层**：设计参考资料（历史上多为 Pencil / `.pen`）
2. **配置关系层**：Manifest / Overrides
3. **打包执行层**：Python
4. **流程编排层**：Trae / AI
5. **输出产物层**：Theme Packages

### 这对当前项目的意义

说明后续实现不应该继续混成一团：

- Web 层不要直接背所有产品差异
- Python 不要承担设计判断
- 设计参考资料不要承担产品矩阵关系

---

## 5.2 Python 打包层的正确职责

历史方案明确指出，Python 层应该负责：

- 读取 manifest 与 override
- 校验输入
- 选择 adapter
- 转换统一中间结构
- 执行打包
- 输出统一日志

而不应负责：

- 自由设计
- 直接替代流程编排
- 每个产品单独复制一份脚本

### 对当前项目的启示

当前项目里的 `theme_builder.py` 还偏向“单体脚本”，后续可以逐步演进为：

- loader
- validator
- adapter registry
- writer

但这是中期任务，不是短期必须立即重构的事情。

---

## 5.3 Manifest / Override 思路

外部资料对 manifest 的定义非常重要，尤其是以下原则：

- 通用关系放 `themes.manifest.json`
- 产品差异放 `product-overrides/*.json`
- 版本差异优先走 override
- 结构差异用 `templateId` / `adapterType` 表达

### 实施意义

这意味着后续如果要扩大产品矩阵，不能继续靠：

- 大量硬编码 `if product === ...`
- 直接复制脚本

必须提前把“关系层”抽出来。

## 6. 对当前项目最重要的落地结论

综合这批资料，当前项目最该优先落实的不是“把所有历史规则都写进代码”，而是先落这四项：

### 6.1 建立项目内统一规则文档

把：

- 颜色规则
- Pen 切图规则
- 页眉关系映射
- 打包层分工

统一沉淀，避免继续散落在外部目录。

### 6.2 建立可复用的规则注册表

至少需要一层项目内统一配置，显式承载：

- Dark-UI 登录页特殊色
- 登录背景导出规则
- 页眉导出规则
- 页眉类型关系映射

### 6.3 预览与截图导出共用同一套规则

特别是：

- 颜色变量
- 图片变量
- 渐变资产
- 文件名与尺寸

不能预览一套、打包又一套。

### 6.4 把冲突点显式列出

不能把资料之间不一致的部分悄悄写进代码。

当前已知冲突包括：

- Light-UI 某些页眉节点命名与映射不一致
- 某些页眉类型在设计参考资料中缺失或只是变体
- 某些设计稿是背景切图源，不是完整 UI 源
